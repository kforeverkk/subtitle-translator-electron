# 原字幕双重身份校验设计

日期：2026-08-04  
状态：待用户最终确认

## 背景

当前程序通过文件名、字幕格式、文件大小和最后修改时间判断 checkpoint 是否属于当前原字幕。这些属性可以识别大多数普通修改，但无法证明字幕内容完全相同。同名文件被另一份同大小、同时间的字幕替换时，程序仍可能错误续传旧 checkpoint，进而把旧字幕的翻译进度用于新字幕。

本次修改需要提高原字幕身份校验的可靠性，同时避免因编码、BOM、换行符或文件时间变化而产生不必要的重译。

## 目标

1. 只有能够证明有效字幕内容一致时，才自动沿用旧 checkpoint。
2. 原始字节完全相同时快速确认身份。
3. 编码、BOM、换行符及无意义空白变化不应强制重译。
4. 字幕文字、时间轴、顺序或影响输出的 ASS/SSA 样式发生变化时必须重新开始。
5. 现有 v1、v2、v3 checkpoint 继续可读，并在能够可靠验证时平滑升级。
6. 哈希、解码和解析必须基于同一次文件读取，避免检查与使用不同版本的文件。
7. 不改变输出字幕命名、翻译配置身份、任务 ID、checkpoint 原子写入及成功后清理等既有机制。

## 非目标

- 不使用相似度或模糊匹配拼接两份不同字幕的翻译进度。
- 不在字幕内容变化后尝试逐条迁移旧译文。
- 不改变用户直接导入独立 checkpoint JSON 时以其内嵌字幕快照恢复任务的既有语义。
- 不把文件路径写入内容身份；文件移动或复制后，只要名称、格式及有效内容符合规则，仍可识别为同一原字幕。

## 身份数据结构

在现有 `source.fingerprint` 中新增以下可选字段：

```ts
interface TranslationSourceFingerprint {
  size: number;
  mtimeMs: number;
  rawHash?: string;
  contentHash?: string;
  contentHashVersion?: 1;
}
```

- `size`、`mtimeMs`：保留，用于旧 checkpoint 解析和诊断，不再作为新版身份的最终证明。
- `rawHash`：原字幕文件字节的 SHA-256 十六进制摘要。
- `contentHash`：规范化后的有效字幕结构的 SHA-256 十六进制摘要。
- `contentHashVersion`：规范化算法版本。只有版本相同的内容哈希才可直接比较。

新 checkpoint 必须同时包含两个哈希和算法版本。旧字段保持兼容，避免旧版本程序或历史 checkpoint 因数据结构变化而立即失效。

## 单次读取与身份生成

程序读取普通字幕文件时执行以下流程：

1. 一次性读取原始 `Buffer`。
2. 立即对该 Buffer 计算 `rawHash`。
3. 使用现有安全编码识别逻辑解码同一 Buffer。
4. 从解码文本解析字幕。
5. 从解析结果生成规范化身份数据并计算 `contentHash`。
6. 将解析结果与完整 fingerprint 一并传入后续 checkpoint 判断和翻译流程。

不得先计算哈希、再从磁盘重新读取字幕进行解析。这样可以避免文件在两次读取之间被修改而产生“哈希属于旧内容、实际翻译的是新内容”的竞态。

## 内容规范化规则

### 通用规则

内容身份必须包含所有会影响翻译输入、时间轴对应关系或最终字幕输出的字段，并排除 `translatedText` 等翻译过程中产生的数据。

规范化结果必须：

- 使用稳定字段顺序；
- 保留字幕条目顺序；
- 明确区分数字、字符串、缺失字段和空字符串；
- 不依赖 JavaScript 对象插入顺序；
- 通过稳定 JSON 序列化后计算 SHA-256；
- 不包含文件编码、BOM、原始换行符或文件修改时间。

### SRT 与 VTT

纳入内容身份：

- 每条字幕的开始时间；
- 每条字幕的结束时间；
- 原文文本；
- 字幕条目顺序；
- 解析器保留且会影响最终输出的头部或 cue 设置。

忽略：

- UTF-8、GB18030、Big5 等编码差异；
- BOM；
- CRLF 与 LF 的区别；
- 文件末尾多余空行；
- 解析后不具有语义的排版空白。

字幕文字内部的有效空格和换行必须保留，不能把可能改变显示或翻译含义的空白随意折叠。

### ASS 与 SSA

除字幕开始时间、结束时间、原文和顺序外，还必须纳入：

- Script Info 中由解析器保留并影响呈现或转换的设置；
- Styles 样式定义及其字段；
- Events 的 Layer、Style、Name、MarginL、MarginR、MarginV、Effect 等字段；
- 内联样式标签和特效代码；
- SSA 转 ASS 所需的原始结构信息；
- 会影响 ASS/SSA 最终输出的附件或头部数据。

纯注释、文件编码、BOM 和换行符形式可以忽略，但不得忽略可能影响字幕样式、定位、特效或转换结果的数据。

## 新版 checkpoint 续传规则

普通字幕文件与 checkpoint 的来源名称、字幕格式首先必须一致。之后按以下顺序判断：

1. `rawHash` 相同：确认原始文件完全相同，允许续传。
2. `rawHash` 不同，但相同算法版本的 `contentHash` 相同：确认有效字幕内容相同，允许续传。
3. `contentHash` 不同：有效字幕发生变化，不允许续传。
4. 新版 checkpoint 缺少完整哈希、哈希格式非法或算法版本未知：不得按新版身份直接续传，转入旧 checkpoint 兼容流程。

`size` 与 `mtimeMs` 只能作为辅助信息，不能覆盖哈希判断：

- 即使二者相同，只要内容哈希不同，就必须重新开始。
- 即使二者不同，只要内容哈希相同，就可以续传。

## 旧 checkpoint 兼容与升级

### 可验证的历史 checkpoint

历史 checkpoint 内含解析后的原字幕快照。程序应从该快照中移除所有 `translatedText`，使用同一套规范化算法计算历史内容哈希，并与当前原字幕的 `contentHash` 比较。

同时满足以下条件时允许续传：

- 来源名称与字幕格式一致；
- 历史字幕快照结构完整且能够规范化；
- 计算出的历史内容哈希与当前内容哈希一致；
- 现有翻译配置 fingerprint 规则允许续传；
- 对 v3 checkpoint，任务 ID 规则仍然满足。

下一次成功写入 checkpoint 时补齐 `rawHash`、`contentHash` 和 `contentHashVersion`，完成原位升级。

### 无法可靠验证的历史 checkpoint

以下情况不得续传旧译文：

- 历史 checkpoint 缺少足够的原文、时间轴或样式数据；
- 字幕快照结构不完整或解析失败；
- 内容哈希不同；
- SSA 历史 checkpoint 缺少安全恢复 ASS 输出所需的原始样式信息；
- 任何情况下都无法证明当前字幕与历史快照等价。

此时使用当前原字幕从头创建干净任务。旧 checkpoint 按现有安全流程备份，只有新的 checkpoint 已原子写入成功后才归档旧文件，防止同时失去旧进度和新进度。

## 直接导入 checkpoint JSON

用户直接选择 `.translation.json` 时，没有独立的当前原字幕文件可供比较。此场景继续将 checkpoint 内嵌的字幕快照视为恢复来源：

- checkpoint 必须通过现有结构校验；
- 翻译配置发生变化时仍按现有规则清除旧译文并重新开始；
- 不伪造当前磁盘原字幕的 `rawHash`；
- 后续保存可以保留原 checkpoint 已有的可靠身份字段，但不得仅根据 JSON 文件本身计算原字幕哈希。

## 文件变化与竞态保护

身份生成与字幕解析来自同一个 Buffer，因此任务开始时使用的是一致快照。任务开始后即使磁盘上的原字幕被修改，当前任务也继续翻译已读取的内存快照，不混入修改后的内容。

如果用户之后重新添加已修改的原字幕，新内容哈希会发生变化，旧 checkpoint 将被拒绝并安全备份。

## 错误与降级处理

- SHA-256 计算失败：任务在发出 API 请求前失败，不生成或覆盖输出字幕。
- 编码识别失败：沿用现有“请转换为 UTF-8”提示，不创建错误身份。
- 内容规范化失败：不允许使用旧 checkpoint；如当前原字幕本身无法规范化，则任务失败并显示明确错误。
- 未知 `contentHashVersion`：视为无法直接比较，尝试从内嵌字幕快照按当前算法验证；无法验证则安全重启。
- 哈希不匹配不是程序错误，不向用户显示技术性报错；按配置变化时的既有机制备份旧 checkpoint 并开始干净任务。

## 性能约束

- 每次添加普通字幕时只读取一次文件。
- 原始哈希和内容哈希各计算一次。
- 不在每个翻译批次或每次 checkpoint 写入时重复读取、解析原字幕。
- 字幕完成前，完整 fingerprint 随内存中的任务状态写入 checkpoint。

字幕文件通常较小，SHA-256 和稳定序列化的成本应远低于一次网络请求。测试需要包含较大字幕样本，防止实现出现不必要的重复计算。

## 与现有机制的关系

以下判断保持独立且全部必须满足：

1. 原字幕身份一致；
2. 目标语言、模型、API 地址、提示词、温度、上下文等翻译配置一致；
3. v3 的任务 ID 与 checkpoint 归属规则一致；
4. checkpoint 文档结构有效。

原字幕身份相同不代表翻译配置相同；任何影响翻译结果的配置变化仍应清空旧译文、备份 checkpoint 并从头翻译。

## 测试要求

### 单元测试

- 相同文件产生相同的 rawHash 和 contentHash。
- 同内容但不同 BOM、编码、换行符产生不同 rawHash、相同 contentHash。
- 修改字幕文字、时间轴或条目顺序会改变 contentHash。
- 修改 ASS/SSA 样式、特效或有效头部会改变 contentHash。
- 修改纯注释不会改变 contentHash。
- `translatedText` 变化不会改变原字幕 contentHash。
- 哈希格式和算法版本接受、拒绝逻辑正确。

### checkpoint 集成测试

- 新版双哈希完全匹配时续传。
- rawHash 不同但 contentHash 相同时续传。
- 大小和时间相同但 contentHash 不同时拒绝续传。
- 大小和时间不同但 contentHash 相同时允许续传。
- 可验证的 v1、v2、v3 历史 checkpoint 能续传并升级。
- 无法验证或内容不一致的历史 checkpoint 被安全备份并干净重启。
- 翻译配置变化仍优先触发现有的干净重启行为。
- 原子写入失败时保留最后一个有效 checkpoint。

### Electron GUI 测试

- GUI 中断任务后，以同一字幕恢复并继续翻译。
- 仅转换编码或换行符后仍能恢复。
- 用同名、同大小、同修改时间但内容不同的字幕替换后，不沿用旧译文。
- ASS/SSA 样式变化后不沿用旧 checkpoint。
- 历史 checkpoint 兼容升级过程不会卡在 pending，也不会提前调用 API 或覆盖旧完整译文。

### 完整回归

运行 TypeScript 检查、全部单元和集成测试、真实 Electron E2E、Windows 构建以及当前构建产物的独立 GUI 冒烟测试。重点确认该修改不影响字幕编码识别、SSA 转 ASS、输出命名、checkpoint 原子写入、配置变化重启、并行 RPM 限制及赞助提示机制。

## 验收标准

- 同名、同大小、同修改时间但有效内容不同的字幕不能续传旧 checkpoint。
- 只有编码、BOM、换行符、文件时间或无意义空白变化时仍可安全续传。
- ASS/SSA 的样式和特效变化能够被识别。
- 可验证的历史 checkpoint 不丢失进度；无法验证时宁可干净重启，也不混用旧字幕。
- 所有身份计算只基于一次读取的字幕快照。
- 新功能通过规定的单元、集成、GUI 和构建回归测试。
