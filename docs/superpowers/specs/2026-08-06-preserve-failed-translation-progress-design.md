# 翻译失败时保留真实进度设计

## 目标

字幕已经部分翻译成功后，如果后续批次失败，界面必须显示最后真实完成的进度，而不是重置为 0%。错误状态同时携带已完成条数和总条数，便于用户判断 checkpoint 的续传位置。

## 根因

每个文件的翻译流程已经维护：

- `totalCues`：字幕总条数；
- `completedCues`：从 checkpoint 读取并在批次成功后递增的完成条数。

正常翻译事件使用这两个值计算进度。但它们目前声明在 `try` 块内部，外部 `catch` 无法读取。错误处理因此把 `progress` 固定写为 `0`，且不发送 `currentCue` 和 `totalCues`。

例如60条字幕已经完成20条，后续批次连续三次失败：

- checkpoint仍保存20条译文；
- 最后的正常进度事件为约33%；
- 随后的错误事件却覆盖为0%。

## 修改规则

- 把当前文件的 `totalCues` 和 `completedCues` 状态提升到 `try/catch` 都可访问的作用域。
- 成功路径继续使用相同变量，不改变批次处理顺序。
- 错误路径按以下方式生成状态：

```ts
const currentCue = Math.min(completedCues, totalCues);
const progress = totalCues > 0 ? (currentCue / totalCues) * 100 : 0;
```

- 错误事件同时发送：

```ts
{
  progress,
  status: "error",
  currentCue,
  totalCues
}
```

## 不同失败阶段

- 输入文件、编码或checkpoint解析失败：尚未得到总条数，显示0%。
- 内容分析在任何翻译开始前失败：显示0%。
- 从checkpoint续传后首次API请求失败：显示checkpoint已有进度。
- 部分批次成功、后续批次失败：显示所有已经完成批次的进度。
- 多并发任务中一个批次失败：现有流程先等待其他在途批次和checkpoint写入，错误事件包含最终完成数量。
- 所有译文完成但最终字幕文件提交失败：显示100%和失败状态，表明失败发生在保存阶段。

## checkpoint 与界面

- 不修改checkpoint数据或写入顺序。
- 不通过界面取最大值掩盖主进程错误数据。
- 不在错误时重新读取checkpoint，避免额外磁盘竞争。
- 界面继续按现有合并逻辑接收主进程事件，因此不需要修改React组件。
- checkpoint临时写入失败仍由现有警告提示；本次进度表示内存中成功翻译的字幕数量。

## 测试

真实 Electron 测试使用60条字幕和单文件并发1：

1. 内容分析成功。
2. 第一批20条翻译成功并写入checkpoint。
3. 第二批连续三次返回空流并失败。
4. 验证错误状态约为33.33%。
5. 验证 `currentCue` 为20、`totalCues` 为60。
6. 验证checkpoint保留且包含20条译文。
7. 完整E2E继续验证重试、续传、关窗取消、输出写入和赞助计数。

## 非目标

- 不改变自动重试次数。
- 不改变每批字幕条数和并发策略。
- 不修改整批IPC参数校验失败的状态流程。
- 不改变checkpoint保存失败时的恢复规则。
