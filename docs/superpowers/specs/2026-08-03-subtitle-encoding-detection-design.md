# 字幕编码安全识别设计

## 目标

避免非 UTF-8 字幕在解析前变成乱码，同时保持现有 UTF-8 字幕、checkpoint、输出命名、SSA 转 ASS 以及翻译续传机制的行为不变。

软件只在能够可靠识别编码时，才自动解码非 UTF-8 字幕。如果识别结果存在歧义或编码不受支持，翻译应在任何 API 请求、输出文件写入或 checkpoint 写入之前停止，并提示用户使用外部编辑器将源字幕转换成 UTF-8。

## 修改范围

本次修改只应用于扩展名为 `srt`、`vtt`、`ass` 和 `ssa` 的源字幕文件。

- 软件生成的 JSON checkpoint 仍严格使用 UTF-8 JSON。
- 所有翻译输出字幕仍统一使用 UTF-8。
- 现有输出路径、checkpoint 路径、源文件指纹和翻译配置指纹均不改变。
- 不增加手动选择编码的界面。
- 不尝试让翻译输出继续沿用源文件的旧编码。

## 问题根因

目前所有源字幕入口都会调用 `fs.readFileSync(filePath, "utf8")`。因此，在 SRT、VTT、ASS 或 SSA 解析器收到内容之前，Node 已经把不符合 UTF-8 的字节替换或错误解码。一旦产生替换字符或乱码，后续解析、语言检测、提示词、checkpoint 和输出流程都无法恢复原始文本。

## 方案比较

### 方案一：严格的分层检测与解码——采用

读取源文件的原始字节，优先使用确定性的 Unicode 识别，只对确认不是 UTF-8 的内容进行统计检测。只有第一候选编码的置信度足够高，并且明显领先第二候选编码时，才接受这个结果。

这样可以覆盖常见旧编码，又不会在 GB 系列、Big5、日文编码或单字节编码难以区分时静默猜测。

### 方案二：始终采用置信度最高的候选编码

这种方式能接受更多文件，但可能静默使用错误编码。一个看起来似乎可读、实际内容错误的字幕，可能在用户发现前就被发送到 API 并保存，因此风险更高。

### 方案三：尝试多种编码，再根据解析后的文本评分

通过字幕格式和语言特征进行评分，可能改善短字幕的识别率，但会引入复杂且脆弱的启发式规则，不属于本次最小化安全修复范围。

## 整体结构

在 Electron 主进程中增加一个专门的字幕解码工具，将字幕 `Buffer` 转换成 JavaScript 字符串。所有源字幕都必须先经过这个工具，再传给 `parseSubtitle`。JSON checkpoint 不经过该工具。

工具返回解码后的文本和标准化编码名称。调用方只把文本传给现有解析器；编码名称只用于诊断，不写入 checkpoint。checkpoint 中本来就保存了标准化后的 Unicode 内容，而源文件身份仍由原始文件大小和修改时间判断。

### 检测顺序

1. 空文件或纯 ASCII 文件按有效 UTF-8 处理。
2. 通过字节顺序标记确定性识别：
   - 带 BOM 的 UTF-8；
   - 带 BOM 的 UTF-16LE；
   - 带 BOM 的 UTF-16BE。
3. 如果检测到 UTF-32 BOM，或者没有上述 BOM 但原始字节含有空字节，则明确拒绝。这样可防止无 BOM 的 UTF-16/UTF-32 被误当成“字节上碰巧有效”的 UTF-8。
4. 没有 BOM 时，使用严格模式验证 UTF-8。只要是有效 UTF-8，就直接采用，不进入统计检测。
5. 仅当严格 UTF-8 验证失败时，才用 `chardet` 分析完整的原始字节。
6. 将检测器返回的编码名称标准化，并且只有同时满足以下条件时才接受：
   - 该名称能够映射到 `iconv-lite` 支持的编码；
   - 第一候选编码置信度不低于 80，检测器的范围为 0–100；
   - 第一候选编码至少领先第二个不同且可解码的候选编码 10 分。
7. 使用 `iconv-lite` 解码完整文件。
8. 如果解码结果包含替换字符、编码映射不受支持，或者本应无损的编码无法通过字节往返验证，则拒绝该结果。

预计支持的常见旧编码包括：GB18030/GBK 系列简体中文、Big5、Shift_JIS、EUC-JP、EUC-KR、Windows-1250 至 1258、Windows-874，以及检测器和解码器共同支持的 ISO-8859 系列。检测器能够识别但 `iconv-lite` 无法解码的 ISO-2022 系列，应当作为不受支持的编码明确拒绝，并提示用户转换为 UTF-8。

为了优先保证准确率，检测时使用完整字幕，而不是只采样开头一小段。现有输入文件大小检查继续负责限制内存占用。

## 数据流程接入

集中式字幕读取工具将替换 `readTranslationInput` 所有分支中直接按 UTF-8 读取源字幕的代码，包括：

- 没有 checkpoint 的全新翻译；
- 同 task checkpoint 无效后的回退读取；
- 从无法验证的旧版 checkpoint 重新开始；
- 旧 checkpoint 恢复 SSA 原始内容时的源文件读取。

新解码的 SSA 原文仍写入现有 checkpoint 的 `subtitle.source.text` 字段，内容为标准化后的 Unicode 文本。这样可以继续支持无损 SSA 转 ASS，同时无需修改 checkpoint v3 结构，旧 checkpoint 也仍然可读。

续传有效且匹配的 checkpoint 时，继续直接使用其中已经解码的字幕内容。源文件指纹仍根据文件原始字节大小和修改时间计算，因此源文件变更判断不受影响。

## 错误处理

增加一个结构化的“字幕编码无法识别”翻译错误码，并在界面层提供英文、简体中文和繁体中文提示。

建议的简体中文提示为：

> 无法可靠识别该字幕的文本编码。请使用记事本、Notepad++ 等工具将字幕转换为 UTF-8 编码后重试。

该错误在翻译预检查阶段抛出。对于这个文件：

- 不发起翻译或字幕分析 API 请求；
- 不创建或覆盖输出字幕；
- 不写入新的 checkpoint，也不创建 checkpoint 备份；
- 任务进入失败状态，不会永久停留在 pending；
- 同一批次中的其他独立字幕仍按照现有批处理错误机制继续执行。

主进程日志可以记录候选编码名称和置信度，方便排查，但用户界面只显示简短提示，也不记录或暴露字幕内容。

## 依赖

把 `chardet` 和 `iconv-lite` 增加为直接生产依赖。两者都在 Electron 主进程中运行，不需要编译原生二进制模块。

即使当前依赖树中已经间接包含 `iconv-lite`，项目也必须直接声明它，因为生产代码不能依赖其他软件包偶然带入的间接依赖。

## 测试设计

### 单元测试

覆盖以下字节级解码情况：

- 带 BOM 和不带 BOM 的 UTF-8；
- 纯 ASCII 字幕；
- 带 BOM 的 UTF-16LE 和 UTF-16BE；
- 带 UTF-32 BOM 的输入和无 BOM 但包含空字节的输入会被安全拒绝；
- GB18030/GBK 系列简体中文；
- Big5 繁体中文；
- Shift_JIS 和 EUC-JP 日文；
- EUC-KR 韩文；
- Windows-1252 西欧文本；
- UTF-8 验证失败且检测结果存在歧义；
- 检测器返回不支持的编码名称；
- 置信度过低或第一、第二候选编码分差不足；
- 解码结果包含替换字符或无法通过无损验证。

置信度边界测试使用可控的候选数据，避免检测器未来升级导致统计结果变化而产生不稳定测试。同时使用具有代表性的真实样本，验证实际检测器与解码器的组合效果。

### 字幕格式集成测试

验证具有代表性的非 UTF-8 `srt`、`vtt`、`ass` 和 `ssa` 文件，都能以正确 Unicode 文本进入现有解析器。

SSA 测试还必须确认样式、原始文本和未知区段在 ASS 输出及 checkpoint 序列化后仍然保留。

### 翻译流程回归测试

验证：

- 全新翻译、重头开始和旧 checkpoint 源文件重读分支使用同一个解码器；
- 匹配的 checkpoint 可以正常续传；
- 修改翻译配置后能干净重启，不会出现新旧语言或乱码混合；
- 所有输出字幕和 JSON checkpoint 都是有效 UTF-8；
- 源文件指纹和输出命名行为不变；
- 编码存在歧义时，在 API 调用和任何目标文件或 checkpoint 变更前失败；
- 同批次其他文件不会永久停留在 pending。

### GUI 与 Electron 测试

使用实际应用测试路径验证：

- 可以选择、预览和翻译能够可靠识别的旧编码字幕；
- 编码存在歧义的字幕会显示本地化的 UTF-8 转换提示；
- 失败时不会创建或覆盖输出文件；
- 界面中的任务明确进入失败状态。

最后运行完整 TypeScript 检查、单元测试、Electron E2E 和构建测试，确认不会破坏此前修复的赞助提示、checkpoint、窗口生命周期、RPM 限制、输出命名和 SSA 转换机制。

## 验收标准

- 现有 UTF-8 字幕的行为完全不变。
- 能够可靠识别的常见旧编码，在解析和翻译前得到正确 Unicode 文本。
- 存在歧义或不受支持的文本不会以猜测结果继续运行。
- 用户能看到明确的“请转换为 UTF-8”提示。
- 编码预检查失败时，不发生 API 调用，也不修改输出文件或 checkpoint。
- checkpoint v1 至 v3 兼容性和 SSA 样式保留机制保持有效。
- 自动化测试在 Windows 和现有 CI 平台上通过。
